# Session report: Phase 1, increment 10 (2026-11-18)

## Delivered
- V10: `payments.stk_request` with database-enforced lifecycle, immutability, idempotency, MSISDN
  and whole-shilling checks, phone-number erasure when final; `MPESA_STK` channel; one M-Pesa
  receipt applied once across STK and C2B; callback `route_ref`.
- Core: `MpesaStkService` + API (create/read for staff; dispatch, submitted, send-failure, result
  for the integration runtime). Receipt application shared with C2B (`applyReceipt`).
- Integration: RabbitMQ consumer for `MpesaStkPushRequested`, `DarajaClient` (OAuth + STK Push,
  outcome classification ACCEPTED / REJECTED / UNKNOWN), STK callback endpoint (store-then-ack),
  `StkResultProcessor`, broker topology declared via Spring AMQP; https enforced for Daraja URLs
  except the test-only simulator.
- `simulators/daraja-simulator` (TEST-ONLY): OAuth, STK Push with password check, STK query,
  scripted callbacks including duplicates and provider errors.
- OpenAPI contract: 6 paths and 8 schemas added, nothing existing changed.
- ADR-0011, runbook `docs/operations/daraja-stk-setup.md`.

## Test evidence (CI run on main, all four jobs green)
Linux: canonical 16, core 81 (9 end-to-end), simulator 2, integration 8 (3 STK end-to-end over
PostgreSQL 17 + RabbitMQ 4 + simulator). Windows: 16 + 72 + 2 (container tests excluded).
Database: 76/76 checks (6 new).

## Issues found and fixed
- The simulator embedded the phone number in the CheckoutRequestID, which tripped the "phone
  number never forwarded" assertion; the simulator now uses an opaque id.
- Review: an OAuth failure was classified UNKNOWN (request left waiting) although nothing was
  sent; it is now a definitive send failure that staff can retry.

## Known gaps (ADR-0011)
Reconciliation of stuck PENDING / DISPATCHED / SUBMITTED requests (STK query job), Daraja sandbox
run, go-live checklist.
